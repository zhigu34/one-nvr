# M1-B 验收边界与实现决策

M1-B 提供固定通道上的摄像头配置修订、测试与切换、连续录像/仅取流、存储池绑定、录像索引、批量导入和本地明文配置导出。WebRTC 实时观看与录像内容播放归 M1-C；Frigate/OpenList 业务归后续阶段。完整实现候选的验收矩阵已通过隔离CI，证据见 [M1-B验证记录](M1-B-validation.md)。

## 自动验收矩阵

| 场景 | 可验证断言 | 实际自动覆盖 |
|---|---|---|
| RTSP 主/子流、60 秒正式录像 | 实际首帧、MP4 媒体结构、ready 索引、字节数与独立文件 | 固定 ZLM 的 contract/publish；真实媒体浏览器通过 |
| 固定槽位、换源与降级 | 通道 UUID 不变，新修订仅应用后生效，子流故障不伪装健康 | switch 与 PG 集成；32槽位实际浏览器通过 |
| 主流切换失败及回滚 | 当前修订保持旧源；旧源也失败时显示故障 | switch 与 PG 集成；实际页面回滚与双源失败/恢复通过 |
| 关闭/恢复录制 | 主流继续可读、无正式录制和事件预录；恢复分配新 run | recovery 与 PG 集成；实际页面通过 |
| 改池、迟到尾片 | 新 run 写新池，旧尾片按原 run/池/修订发布 | switch/recovery/PG 集成 |
| 重复 Hook 与发布崩溃 | 幂等 inbox/索引；移动前后可恢复、冲突不覆盖文件 | publish 与 PG 集成；实际发布进程移动前后SIGKILL恢复通过 |
| DB 停机 | 已有 ZLM 录像继续，Hook 私有 spool 持久化，恢复可发布 | PG/Spool 集成；真实DB容器停机与spool重放通过 |
| API/Worker 独立、共同重启 | 同一有效上游 run 被接管，历史索引不变 | PG 对账测试；API/Worker独立和共同重启通过 |
| ZLM 重启 | 新物理 session/run，旧文件继续可检索 | 外部代理缺失已验；实际ZLM容器重启新session/run通过 |
| TLS 自动更新 | 两个通道持续产片、ZLM 容器 ID 不变、证书实际切换 | 网关换证已验；双通道持续产片及同一ZLM容器通过 |
| 可选模块关闭/不可达 | 基础取流、录制无模块依赖 | 部署开关已验；服务缺失及新连接恢复通过 |
| 私有媒体边界 | 未授权 Hook/原生 MP4/RTC 不可经公共网关访问，重定向越界被拒绝 | 固定 ZLM/PG 集成；实际联合网关核对通过 |
| 三行批量导入 | 成功/失败/冲突分别保留，关闭页面不停止任务，重试不重放成功行 | import 实际媒体与 PG 集成已验 |

测试全部使用隔离私有数据卷和模拟媒体；32 槽位映射只验证产品数据模型。两个主/子流样本不构成 16–32 个摄像头的吞吐、硬件稳定性或真实海康 NVR 验收。

## 已落实的决策

- `.env` 只配置部署与模块开关，摄像头与目录池通过控制面板/批量导入管理。密码加密持久化；查看与明文导出仅管理员独立请求，不进入共享查询缓存。
- 后端保存草稿、测试、应用保持独立；界面提供“保存并测试”，保存成功后自动提交连接测试，失败可重试，测试通过后仍须显式应用。新源失败通过持久阶段回滚。相同配置与更名不会无意义重连。普通录制策略不因换源、重启或导入被重置。
- 每个实际录制启动分配不可变 run；片段按 run 保存通道、源修订、存储池和时间规则。晚到尾片不能绑定到新源或新池。
- 路径日期与文件名使用录制 run 冻结的站点 IANA 时区，数据库时间使用 UTC。设置更改不改写已有文件与历史归属。
- 源/写入/码率观察会过期，未知不等于可用。容量安全线不把未知码率视为零。管理请求失败不能被当作已确认媒体不存在。
- M1 不自动删除正式录像。运行时写入状态和中断记录可查询；完整性评分、归档和保留策略另行实现。
- 通道总览采用可搜索、筛选和选择导出的紧凑表格；工作台按摄像头连接、录像设置、历史与诊断分区。常用凭据留空保留，输入新值即可替换；高级端口、清空和历史恢复收起。切换通道会中止迟到的表单回填，离开历史页会清除已展示的凭据。
- 存储池登记与检查保留在主界面，修改和诊断收起；检查任务反馈不再因池版本刷新而丢失。仍保留 M1-A 延期项：用户操作反馈随版本重挂载，以及时区搜索预览。
- 录像计划页的「绑定 / 应用 / 批量应用」遇到过期的存储池写入证据（真实写入证明仅 30 秒有效）时，页面自动补跑一次真实存储池检查并重试该操作，操作者只需点一次；检查失败时显示具体原因（如需先完成摄像头连接测试）。服务端的证据门槛、时效与拒绝语义保持不变（2026-10-10，用户裁决「我要的是一切顺利操作」）。摄像头配置页的「测试并启用 / 保存并启用」已做同构修复（`applyWithPoolRecovery`：同一真实检查 + 重试，未绑池回退默认池）；批量导入的「开启连续录像」入口同属一族，暂未改。

## 存储写入检查改为按站点可关（2026-10-10，用户裁决，覆盖 M1-B Task 7/最终裁定）

**背景与裁决**：用户提出「我没有这么高可靠性需求，直到落不了盘报错停止录像就行」，要求把存储写入预检做成可选开关。这**明确覆盖** `docs/M1-B-rulings.md` 中「不延长 TTL、不用推断证据、不放宽 API 准入门槛」的既有裁定——原文保留作为历史依据，本决策为其现行替代。

**开关**：`sites.require_storage_write_proof`（迁移 `0012`，默认 `true`）。默认值等于既有已验收行为，因此现有站点、既有 CI 验收与已裁定语义在新库上不变。可在「系统设置 → 存储写入检查」切换，改动即时生效（每次操作读一次站点行，无需重启）。

**关闭后放宽的**：仅「准入时要求一次已验证的 MP4 真实写入」。
- 绑定存储池、应用/开启连续录像不再等待 `zlm` 证据，缺少可用摄像头时也能先绑定、先设录像计划。
- `idle_pools` 的 3 秒临时探测不再运行（否则空闲池会每 30 秒写一次盘，正是本开关要避免的成本）。

**关闭后不放宽的（两条都必须在）**：
- **容量与进程可观测性**：`api`/`worker` 两条进程样本始终必需，TTL 仍 30 秒。它们才是「磁盘写满」可被发现的依据；去掉则磁盘满时不会停录。
- **停录看门狗（本轮新增）**：录像持续约 3 分钟没有任何 MP4 完成回执时，停止录像并把通道置为不可用（`recording_output_stalled`），不再只显示灰色「未知」而放任空转丢录像。触发了这一失败模式，才是「落不了盘就报错停止录像」真正成立的地方。

**代价（明确记录）**：关闭写入检查后，一个 api/worker 可写但 ZLM 不可写的存储池会被接受并开始录像；失败要到看门狗发现（约 3 分钟）才暴露，这段时间的录像是真实丢失且不可恢复。开关把「提前 3 秒证明」换成「出问题时延迟约 3 分钟发现」。

**验证**：`tests/integration/storage_admission_test.go` 固定两态边界（关闭时 zlm 失败仍可用、任一进程样本缺失即不可用、过期样本一律不可用、站点 PATCH 往返）；`internal/recording/watchdog_test.go` 固定停录判定边界（含「新 run 等首片段」不误停）。运行期真机行为（真实摄像头 → ZLM → MP4）仍以 CI 的媒体/联合验收 job 为准。
