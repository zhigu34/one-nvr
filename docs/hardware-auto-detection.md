# one-nvr 部署硬件自动探测

日期：2026-10-04；版本：1。正式版部署设计，尚未实现；M0 保持原 CPU/Intel 配置方式。

## 1. 默认策略

用户希望运行 deploy.sh 时自动识别硬件并生成设备覆盖配置，普通部署不用手选 CPU/Intel 档案。`ONE_NVR_HARDWARE_PROFILE` 默认为 `auto`，可省略；已有 `cpu`（强制 CPU 路径）、`intel-igpu`、`nvidia` 作为高级覆盖项保留，覆盖项也必须实际测试，不等于忽略检查。

仅 `ONE_NVR_FRIGATE_ENABLE=yes` 执行检测硬件流程；no 时不枚举/测试 GPU、不要求设备/模型/Frigate 镜像、不生成 GPU 映射。ZLM 基础取流/原码录像不因缺 GPU 受阻，探测容器为一次性工具，不增加常驻服务。

自动策略输出独立的解码选择、推理选择、设备映射、测试依据和失败/未测结果，不用一个“GPU 正常”覆盖所有能力。规则与实际执行设备必须可见，不能只看 CPU 型号、设备节点存在或容器启动成功。

## 2. 探测流程与自动选择

1. 在 Docker daemon 所在的目标 Linux 主机枚举实际设备。使用 sysfs 的 vendor/device/PCI 地址/driver 关联 DRM render 节点，记录内核、设备权限和 Docker 平台；不依赖宿主安装 lspci、Python、Go 或 vainfo。NVIDIA 另记录容器运行时可用性和设备标识。不把 CLI 所在另一台机器的硬件当作 daemon 硬件；无法获取远端宿主清单则明确 unknown。
2. 对属于当前锁定镜像/适配范围的候选，生成最小设备映射，用同一 Frigate 镜像/驱动/用户身份启动有超时的一次性探测容器。只授予候选设备，不使用 privileged，不安装或更改宿主驱动，不让 API/Worker 挂 Docker socket。宿主采集只能只读查询，不修改系统。
3. 分别测试解码和模型。解码用随发布提供且带来源/hash 的短 H.264/H.265 样本，验证真实帧解码与实际后端；推理用明确绑定 CPU 或某一 GPU 的兼容模型/固定输入，验证模型加载和推理，并报告实际设备，不使用 AUTO 让上游自行隐式降级。缺少某模型/编码样本则对应结果未测，不标通过。
4. 初次自动选择优先选取已通过的 Intel 解码和 OpenVINO GPU 候选；无适配范围内的硬件加速候选时选择软件解码与 OpenVINO CPU 候选，CPU 同样需兼容测试。解码和推理各自决定，允许一种加速而另一种 CPU，报告真实组合。某项 GPU 候选测试失败则该项报告异常，不默用 CPU 冒充 GPU 成功。
5. 多个同类候选以稳定设备标识排序，选择首个通过的候选并记录规则；推理设备必须绑定到实际被映射的目标，不能用含多个设备的泛称 GPU 而无法确认执行设备。全部失败不选择任意设备。提供高级覆盖用于指定已发现设备；请求未发现/不匹配的设备明确拒绝。
6. 校验生成的 Compose 覆盖与 Frigate 配置，保存硬件报告，再部署所选服务。候选还未通过实际摄像头/负载测试时，只标“样本自检通过”，不能标“16/32 路检测已认证”。正式业务流仍在 M3 通过 ZLM 检测流复验，并记录抓拍/事件、实际编码和负载。

自动选择面向任意已枚举硬件，不限定机型；首轮验证样本为用户现有的两台机器，覆盖“无可用加速设备”与“Intel 核显可用”两条路径：N5105 的 VAAPI 与 OpenVINO GPU 分开验证，EPYC 无可用加速设备采用软件解码/CPU 候选，两条路径都必须实际测试。样本机器不代表部署范围；服务器显示卡或不适配的设备列入清单并注明不适用，不当视频加速器。

保留此前“AMD 检测先不管”的验收边界：M1-A 真机验证顺序上优先 N5105 样本（排序仅指验证顺序，不是部署范围限制）；EPYC 的自动枚举/CPU候选与失败隔离可验证，但其实际推理兼容/负载仍可标未测，不作为本阶段退出门槛。未测不得显示该机器智能检测已就绪。

NVIDIA 和 AMD GPU 可识别，但自动启用以已登记的具体镜像/驱动/模型组合为准。当前标准 Frigate 镜像基线不能自动冒充已验证 TensorRT 镜像；新增 NVIDIA 推理路径须单独锁定正确镜像/digest并验收，未完成时报告未认证，不自动拉 latest/其他变体。OpenVINO CPU 在 AMD 上的兼容性同样需要实际测试，不复用 Intel 结果。

## 3. 首选、失败与重部署

没有可用 GPU 候选而首次选 CPU，是明确记录的初始自动选择；不是已生效 GPU 故障后的无声降级。已有成功硬件配置时，重复 deploy 优先复验原来的稳定设备/组合，重启不因为 render 节点编号变化或新设备出现而随意换设备/模型。

原设备消失、权限/驱动改变或已选择的 GPU 失败时，保留期望配置及故障证据，不自动改为 CPU。能恢复原组合则恢复，否则智能检测不可用/需处理；管理员可修复部署环境，或明确改为 CPU 覆盖后重新测试。核验失败返回模块部分失败报告，基础服务保持就绪，不将 Frigate_ENABLE 悄悄写成 no，也不把未配置检测通道当成硬件已验证。

首次部署可启动尚未配置检测通道的面板和服务；无法完成模型/设备自检显示该项待验证/异常并限制对应检测配置。若硬件配置会使 Frigate 无法启动，只报告该模块失败，不影响 gateway/api/worker/postgres/zlm。检测通道、模型和业务规则仍在界面配置，自动探测不创造摄像头或自动对所有 32 路启用检测。

生成覆盖配置仅控制 Frigate 的设备/运行时；重新部署因设备映射变化需要重建 Frigate 时记录检测空窗，不重建 ZLM。`deploy.sh --check` 可执行只读清单和一次性核验、保存脱敏报告，不启停生产业务服务。

## 4. 配置与面板

最小 .env 不要求硬件选项。需要显式写出时：

```dotenv
ONE_NVR_FRIGATE_ENABLE=yes
ONE_NVR_HARDWARE_PROFILE=auto
```

高级覆盖不再是安装必填步骤；必须与枚举的设备匹配，设备选择记录稳定标识与实际节点。部署参数控制容器设备映射，界面保存解码/模型/推理业务配置，不能出现两处静默互相覆盖。

“系统设置 → 智能检测 → 硬件”显示宿主清单、自动/手动来源、所选映射、解码/推理各自期望与实际设备、样本/业务测试范围、镜像/模型摘要、最近测试/失败原因和是否需要复验。M1-A 提供部署探测结果/能力状态；正式检测硬件/模型配置发布与业务事件验证仍属于 M3。无指标显示未知，失败记录保持可查。

## 5. 验收

- 检测关闭不启动探测工具，不要求 GPU/模型；默认 auto 和显式覆盖解析正确。
- 改变 render 节点编号、多个 Intel 设备、EPYC 加服务器显示卡均按稳定身份和能力选取，不按 CPU 品牌/固定D128推断。
- 有设备但未透传、访问拒绝、缺驱动/容器运行时、错误模型、某编码不支持分别报告，解码成功不能替代推理成功。
- 无 GPU 的初次 CPU 选择有记录和兼容测试；已生效 GPU 后来失败不悄悄降级，模块失败不停止核心看/录。
- 未锁定的 NVIDIA 镜像/模型组合不会被自动启用；候选/未测/样本通过/业务负载认证分开。
- 四种模块组合常驻容器数仍 5/7/6/8，部署工具退出；报告不含摄像头凭据或密钥，重复部署保留有效业务配置。
