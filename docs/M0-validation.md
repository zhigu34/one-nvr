# one-nvr M0 真机验证清单

依据：PRD 的 M0 范围。状态：验证计划，尚未执行真机验证；初始 Compose 实验包已提供，版本为待验证候选，不表示已认证通道容量。

部署按 [M0 部署说明](../deploy/m0/README.md) 只编辑 `.env`，填写 camera1…camera32 完整 RTSP URL、服务器 IP、目录与 CPU/Intel 档案；单个 Compose 自动完成一次性初始化和常驻服务启动。宿主无需 Python/OpenSSL。工具基础镜像按用户要求使用 `python:3.12-slim`，镜像构建与真机兼容性仍待实际部署验证。

网络受限时使用部署目录的 `./deploy.sh`：检查本地 Python 镜像架构，选用 Engine 内置构建器，只构建一次共享工具镜像；安装源通过 `.env` 可配置，运行镜像须预先准备。自动化构建协调测试不等于真机构建或网络速度验证。

M0 要验证 ZLM 正式录制、Frigate 仅检测、one-nvr 管理索引/事件的分工是否成立，并发现影响后续实现的接口与硬件问题。先用 2 路真实摄像头跑通链路；完整 shadcn-admin 面板、32 路容量认证和全部 P0 功能属于后续里程碑。

## 1. 准备条件

- 2 台实际摄像头，提供 IP、RTSP 端口、账号/密码和主/子流路径；至少一路能进行人或车的现场触发。
- EPYC 7402 和 N5105 的实际内存、系统/内核、驱动、GPU/设备映射信息；裸机或虚拟机及直通方式分别登记。
- 独立测试目录池、足够测试容量；可选 WebDAV 测试命名空间用于归档兼容探测。
- 宿主机时间同步，从测试浏览器可达的 HTTPS/媒体地址，以及摄像头网络连通性。
- 候选 ZLM/Frigate 镜像的精确版本与 digest、模型格式/摘要、MQTT/数据库版本、浏览器版本。
- 最小 Compose、ZLM/Frigate 适配脚本或薄 API、事件接收与索引持久化原型、临时授权播放页面。首轮工具见 [M0 部署说明](../deploy/m0/README.md)，当前实现范围与未覆盖实验在该文件中明确列出。

初始参考码流为主流 H.264 1080p、20 FPS、约 4 Mbps；子流 H.264 640×360、10 FPS；检测 5 FPS。设备不能提供时记录实际参数与差异，不能用不同负载的数据冒充同档结果。

## 2. 核心实验

| 编号 | 要做的实验 | 通过标准/必要结果 |
| --- | --- | --- |
| M0-01 | 启动候选 Compose，检查容器网络、目录持久化、组件接口、模型及硬件 | API/接口返回值保存脱敏样本；容器实际能访问所需目录/设备；镜像和模型版本可重现；不能只以容器运行中认定成功 |
| M0-02 | 把八列摄像头配置生成主/子 RTSP，经 ZLM 拉流，供 Frigate 与浏览器消费 | 密码特殊字符、路径 query 拼接正确；主/子流各由 ZLM 建立上游连接，Frigate 消费 ZLM 内部 RTSP；分别报告实际媒体进展，不直接把 TCP 可达当在线 |
| M0-03 | ZLM 连续生成约 60 秒 MP4 分片，捕获完成回调并建立最小索引 | 正式视频由 ZLM 生成；实际起止/轨道/GOP/时间戳可探测；重复回调不重复登记；丢弃一次回调后扫描能补索引；无故障与注入故障的缺口分别记录 |
| M0-04 | Frigate 开启目标检测/抓拍，关闭 record；现场触发人/车、区域进入/停留 | 捕获实际 new/update/end/区域消息与抓拍，记录提供/缺失字段；不依赖 Frigate recording/clip；镜像目录与状态确认未生成第二套正式录像；事件接收先持久化 |
| M0-05 | 验证事件持久化、抓拍 HTTP 获取、MQTT 中断与 Frigate 重启 | 分别记录有/无抓拍事件是否能经 API 恢复，哪些消息/状态无法补回；断连恢复能对账已持久事件，无法恢复的窗口明确标缺口，不能承诺 MQTT 自动重放全部历史 |
| M0-06 | 将事件时间关联 ZLM 分片，测试前 10 秒/后 20 秒窗口及跨片播放 | 人/车动作对应实际画面；测量事件与录像偏差/不确定性；录制未开始或真实缺口处不伪造前录；未完成尾片显示生成中，片段就绪后补关联 |
| M0-07 | 用真实桌面浏览器验证授权直播、MP4 回放、跨片拖动和短片导出 | H.264 基线可播放；从用户网络验证 WebRTC 地址/端口；跨片实际媒体无整段遗漏；退出/撤销权限后按 PRD 拒绝新请求并关闭既有会话；H.265 如有则单独报告能力 |
| M0-08 | CH01 从摄像头 A 切换到 B，再让 B 测试/应用失败 | 测试期间 A 持续录制；切换后 CH01 历史仍可查；旧尾片/旧事件按原源会话登记；失败回滚 A；CH02 不重建录制；缺口与区域需重校准状态明确 |
| M0-09 | 分别中断摄像头主/子流，停止 Frigate/MQTT/适配进程并恢复；重启 ZLM 与测试主机 | 检测服务故障时 ZLM 既有录制继续；媒体服务/主机停止的真实缺口可定位；恢复后重建期望拉流/录制及索引；主/子流与录像/检测状态分别报告 |
| M0-10 | 测试目录不可写、媒体缺失/损坏、监测停止和数据库短时不可用 | 识别池阻断、坏片/缺片、待核验和监测未知；15 秒观测不声称精确定位亚秒边界；扫描可修复生成证据但不伪造源可用性；不把组件/存储故障自动归责摄像头 |

M0-05 是关键版本门槛：Frigate 关闭录像后能实时发事件，不等于所有事件都具备可恢复的持久历史。若实际能力不足，保留 one-nvr 接收后持久化与明确缺口的设计，评估是否需要调整版本/契约；不得为掩盖问题重新启用 Frigate 正式录像。

## 3. 两款机器分别验证

| 机器/条件 | 初始候选 | 必须观察 |
| --- | --- | --- |
| EPYC 7402，未确认可用独显 | 软件解码 + OpenVINO CPU，兼容轻量模型 | AMD CPU/模型运行是否兼容、实际 CPU 执行设备、解码 CPU 与推理资源、跳过帧、内存/共享内存、事件延迟 |
| N5105，核显可访问 | Intel VAAPI 解码 + OpenVINO GPU，同等模型/现场条件 | 设备/权限与实际 GPU 执行、共享核显解码/推理负载、CPU 运动分析开销、跳过帧、内存/共享内存、事件延迟 |
| EPYC 如有兼容 NVIDIA 独显 | NVDEC + ONNX/TensorRT 候选 | 驱动/镜像/模型兼容、支持的码流、实际设备、显存、解码/推理负载与延迟；未提供显卡则不填写 GPU 测试通过 |

每台先测 2 路，稳定后可进行 4/8 路探索；增加通道需要真实不同码流并记录现场活动。复用同一静止流可以测资源趋势，但不能替代多路真实摄像头或全活动场景认证。比较硬件时保持模型、输入参数和活动条件可比，不可用模型降级后结果宣称纯硬件提升。

建议每种拟采用档案完成 2 路连续 24 小时观察，并穿插检测、回放及故障恢复；这是 M0 初步稳定性证据。PRD 中 16/32 路、72 小时综合负载和现场准确率仍需在后续容量/发布验收完成，M0 不直接给出机器最大支持路数。

## 4. 可提前进行的归档/到期验证

有 WebDAV 测试服务时，先测一个完整 ZLM 分片：PUT → 存在/长度验证 → Range 回放 → 删除本地测试副本后继续云端播放 → DELETE 与不可见验证。记录 Range/DELETE/回收站能力，不使用 Frigate 导出接口代替原片。该探测不替代 M2.1 的手动/定时上传、重试/租约/保护和完整故障验收。

90 天事件索引和 365 天云副本无需等待真实期限：在隔离的测试实例使用受控业务时钟/构造时间验证边界，保持媒体时间与宿主系统时间的测试目的分开。确认事件索引到期不删除录像、更早录像仍可按通道和时间检索；完整业务清理状态机仍在对应里程碑验收。

## 5. 留存证据与出口

每项实验保存：执行机器/版本、时间、输入参数、步骤、脱敏消息/API 样本、实际媒体时间与故障证据、关键资源/延迟指标、结果和未解决事项。结论状态使用“通过 / 失败 / 有条件可用 / 未测试”，不把缺少指标写为 0 或已通过。

交付三份结果：

1. 上游版本/接口/模型与两款机器的兼容矩阵，包括关闭 Frigate 录像后的事件恢复边界。
2. 端到端链路与故障报告，包含至少一个人/车事件关联 ZLM 原片的实例、跨片回放、切换/重启与真实缺口。
3. 实测部署参数与未解决问题清单：设备映射、共享内存、内存负载、路径/网络配置、测试通道数；明确哪些问题阻止进入后续开发、哪些需要容量阶段复验。

关键架构出口为 M0-01…10 有足够证据支持指定分工；硬件失败可将对应档案标为未适配，不能隐藏失败或直接宣称两款均支持。播放、时间关联、源隔离、录像独立性存在阻断时先修正适配/版本与 PRD，再进入正式模块开发。
